"Required by" names the first profile in which the operation must do real work; a REQUIRED operation that a read-only export must merely reject correctly is required by `read-only-local` for rejection and by a later profile for implementation. Current support describes the dispatcher today.[^dispatcher] Evidence names the focused test file (`Nfs4.test`, `Profile.test`), the pynfs baseline (`pynfs`), or a client result.

## Staged write-open state

The internal NFS handler can enable write access for existing regular files. An `OPEN` records the open owner's read and write access alongside its deny bits. Conflicts compare new access with held denials and new denials with held access, including the same owner's earlier open. A repeated `OPEN` can extend access by opening only the newly requested mode and retaining the earlier handle. This permits an upgrade when permissions changed after the first open; interruption leaves the original handle usable. `OPEN_DOWNGRADE` keeps only a nonempty subset of held access and denial; `CLOSE` and lease revocation release the reservation. `READ` with a write-only stateid returns `OPENMODE`. Session replay prevents a retried `OPEN` from applying twice.[^dispatcher][^tests]

This mode is not exposed by `NfsServer`. The public read-only profile and the table above still reject write opens with `ROFS`, and `WRITE` remains `ROFS`. The writable export requires qualified durability and the remaining writable operations under [writable export scope](../../decisions/nfs/writable-export-scope.md "constrained by").

The same staged handler grants write byte-range locks when writable mode is enabled. `LOCK` and `LOCKT` return `DENIED` with the conflicting NFS client's owner, type, and range; read locks can overlap each other. For one lock owner with multiple open stateids, the last `LOCK` assigns each byte to its open stateid, and `LOCKU` releases the owner's bytes across those stateids. Other stateids keep their sequence numbers. A lock owner can replace or release part of its own range. Range splits remain subject to `maxLocks`, while owner state remains subject to `maxLockOwners`. Waiting lock types receive an immediate conflict response and do not create a queue. `CLOSE` requires held ranges to be unlocked first; successful close, lease expiry, and client revocation invalidate the associated lock stateids.[^dispatcher][^lock-tests]

## Writable-profile error rules

These rules prepare the writable profile; the dispatcher currently rejects the listed mutations with `ROFS`. They do not claim that the operations are implemented. RFC 8881 Section 15.2 lists valid errors per operation, but does not prescribe a general order when several faults coexist. The validation order below is a project decision; preserve the existing read-only structural checks before `ROFS`. The adapter translates core failures in the context of the operation, after NFS filehandle, stateid, name, and attribute validation.

| Operation | Writable-profile rule                                                                                                                                                                                                                                                                                                                                                                                 |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CREATE    | A name already present is `EXIST`; invalid names retain the existing name-specific statuses. Directory/type, authorization, and capacity failures use only statuses valid for CREATE.                                                                                                                                                                                                                 |
| LINK      | A destination name already present is `EXIST`; a directory source is `ISDIR`; a future explicit hard-link limit would be `MLINK`. No such limit or core failure exists yet.                                                                                                                                                                                                                           |
| OPEN      | GUARDED4 on an existing name is `EXIST`. EXCLUSIVE4 and EXCLUSIVE4_1 reuse an existing object when its verifier matches; a different verifier returns `EXIST`. Ordinary mode denial is `ACCESS`; ownership-specific `PERM` handling is deferred with writable operations. Validate the open claim, stateid, name, and current object before translating a core failure.                               |
| REMOVE    | An empty-directory requirement failing is `NOTEMPTY`. Missing names are `NOENT`. The existing name and current-directory checks precede the mutation.                                                                                                                                                                                                                                                 |
| RENAME    | An incompatible existing target or a nonempty target directory is `EXIST`, as Section 18.26.3 explicitly requires. Core may instead report `IsDirectory`, `NotDirectory`, or `NotEmpty`; the RENAME implementation must translate these target-conflict cases with source and target context. A non-directory _source or target directory handle_ remains `NOTDIR`. Missing source names are `NOENT`. |
| SETATTR   | Ordinary access denial is `ACCESS`. `PERM` applies only when the writable operation identifies an ownership restriction; core's current `AccessDenied` alone does not distinguish the two. | WRITE     | Validate the current filehandle and stateid before writing. Core capacity and size failures translate to `NOSPC` and `FBIG`; ordinary permission denial translates to `ACCESS`.                                                                                                                                                                                                                       |

Client-supplied filehandles are classified during `PUTFH`: malformed or unknown handles answer `BADHANDLE`, a handle from a different export generation answers `FHEXPIRED`, and a formerly valid deleted object answers `STALE`. Invalid or foreign core references after that boundary are adapter faults and answer `SERVERFAULT`. `StaleReference` already maps to `STALE`. NFSv4.1 has no `LOOP` status; the adapter's current reference-based read path does not follow symbolic links, and its generic substitute for a future core `SymlinkLoop` is `INVAL` where the operation allows it. `NoData` and local handle/caller misuse remain internal faults. These rows must be checked against Section 15.2 when each writable operation is implemented.

## Reading the ledger

Every REQUIRED forward operation now has an operation-valid answer for a read-only export. Three REQUIRED operations are deferred to `stateful`, each with an interim rejection that Section 15.2 allows. The backchannel sends CB_COMPOUND with CB_SEQUENCE; CB_RECALL_SLOT is excluded because the slot table is never reduced. The five must-not-implement operations and every unimplemented OPTIONAL operation return `NFS4ERR_NOTSUPP`, and `NFS4ERR_ROFS` is issued only for the operations Section 15.4 lists.[^rfc8881-15] The Linux server's own status table is the presentation precedent.[^knfsd]

Behavior claims are grounded in the dispatcher and the two protocol test suites, and the [external suite baseline](../../evidence/nfs-external-suite.md "evidenced by") records which rows a raw-RPC client has exercised.[^dispatcher][^tests][^profile-tests] Cross-cutting rules live in the [protocol rules ledger](nfs-protocol-rules-ledger.md "depends on"), and attribute rows in the [attributes ledger](nfs-attributes-ledger.md "depends on").

[^rfc8881-17]: Table 16 and Table 17 define REQ, REC, OPT, and MNI; Section 17 states that OPTIONAL operations return `NFS4ERR_NOTSUPP`.

[^rfc8881-15]: Section 8.8 and Section 15.2 require `NFS4ERR_NOTSUPP` for the five NFSv4.0 operations; Section 15.4 lists the operations that may return each error.

[^dispatcher]: The opcode table, `decodeOperation`, and the `execute` switch define which operations exist and how they answer.

[^tests]: The compound suite drives `handler.compound()` with hand-encoded XDR and covers negotiation, replay, filehandles, directory reads, opens, reads, and mutation rejection.

[^profile-tests]: The profile suite covers the operations added for read-only completeness, the client-record cases, and the session guards.

[^lock-tests]: The lock suite covers two-client conflicts, disjoint ranges, partial replacement and unlock, replay, owner isolation, limits, close, and lease cleanup.

[^knfsd]: The kernel documentation publishes Table 16 with an implementation-status column.
