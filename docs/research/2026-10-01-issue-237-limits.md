# Issue 237 limits and commit-provider research

Researched 2026-10-01 against the current checkout, the installed Effect 4.0.0 source, and [issue 237](https://github.com/lloydrichards/effect-virtual-fs/issues/237). This note records design recommendations. It does not change runtime behavior.

The parent investigation reproduced `LiveVolume.open` with requested pending limit 1 and watch limit 2 returning effective values 64 and 256. It also ran the existing live-volume and internal live-image suites: 27 tests passed. Existing tests therefore do not detect this option drop.

## Recommended limits policy

Keep `maxPendingOperations` and `maxWatchEvents` as runtime options. Reopening the same stored image with different runtime limits should succeed and use the new values. The live image already stores only the four capacity limits. Keeping that format avoids a migration and preserves version 1 decoding. Identity and capacity limits still determine store compatibility. Sources: [live runtime schema](../../packages/core/src/internal/tree.ts), [live codec](../../packages/core/src/internal/liveImage.ts), [issue scope](https://github.com/lloydrichards/effect-virtual-fs/issues/237).

Add one core-internal module for normalized limits and defaults. `fromOptions` should receive validated options and produce effective limits. `fromStored` should recover capacity from the image and receive runtime settings from the current open. `toStored` should omit runtime settings. `compatible` should compare normalized capacity values, plus an explicitly requested identity. This removes today's raw-options comparison, which rejects opens with omitted capacity options even when both stored and requested values mean unlimited or the default file ceiling. Sources: [open compatibility check](../../packages/core/src/LiveVolume.ts), [engine construction and restoration](../../packages/core/src/internal/virtualFileSystem.ts), [public option schema](../../packages/core/src/Volume.ts).

The omitted-option compatibility fix changes observable behavior and deserves an explicit decision. Recommended behavior is that omitted `maxBytes`, `maxEntries`, and `maxPathBytes` mean unlimited, while omitted `maxFileBytes` means 4,294,967,295 bytes. Compare those meanings consistently across new and reopened volumes. Explicitly requested mismatches must continue to fail with `IncompatibleStore`. Source: [capacity contract](../../.okf/contracts/capacity-and-limits.md).

Preserve the existing public `LiveVolume.openImage` four-argument call. The high-level `open` can use an internal options-aware opening function, so supplying runtime settings does not force a public API change. Without runtime options, low-level image opening should retain defaults. Source: [public live-volume API](../../packages/core/src/LiveVolume.ts).

## Acceptance detail that needs clarification

`maxPendingOperations: 1` currently admits two total operations: one active operation and one waiting operation. A third concurrent operation fails with `VolumeBusy`. The existing contract says that the default 64 permits 65 callers, and the engine uses `maxPendingOperations + 1`. The issue's requirement that the second concurrent operation fail conflicts with that established behavior. Recommended interpretation is that the second waiting operation fails. Sources: [watch admission decision](../../.okf/decisions/core/watch-event-overflow.md), [engine admission](../../packages/core/src/internal/virtualFileSystem.ts), [watch tests](../../packages/core/test/Watch.test.ts).

`maxWatchEvents` is a per-subscriber bound. Overflow places a rescan marker in the queue and drops further changes until the consumer takes it. The smallest valid value is 2. A durable-open regression should register a subscriber, fill its queue under a requested small bound, and observe rescan behavior. Checking only `volume.limits` would not prove the hub uses the option. Sources: [watch hub](../../packages/core/src/internal/watchHub.ts), [option validation](../../packages/core/src/Volume.ts), [watch overflow tests](../../packages/core/test/Watch.test.ts).

## Empty image and package ownership

Construct the empty `VolumeState`, identity, epoch, secret, initial timestamp, and effective limits directly, then encode the value. Today's `prepareEmptyLiveImage` constructs the whole engine to obtain bytes. Direct construction follows the accepted decision that converters operate between the tree and value. Preserve secure naming, clock validation, root metadata, and argument-error retargeting. Sources: [engine initialization](../../packages/core/src/internal/virtualFileSystem.ts), [persistent tree rebuild decision](../../.okf/decisions/core/persistent-tree-rebuild.md).

Leave snapshot decode budgets and memory tree-transfer projections in their owning packages for this issue. Decode limits describe document-processing budgets, not volume settings. Tree transfer belongs to memory and has its own finite sentinel for unlimited byte limits. Moving that policy into a core-internal module would require memory to reach into core internals or expand the public API. Sources: [budget projections](../../packages/core/src/internal/budget.ts), [memory transfer projection](../../packages/memory/src/internal/treeTransfer.ts), [package dependency decision](../../.okf/architecture/package-dependency-model.md).

Keep `maxImageBytes` checks in both core and persistence stores. The core rejects oversized candidates before storage. SQLite and R2 have independent configured bounds and expose `LiveImageStore` directly, so their defensive checks serve a different boundary. Consolidating volume-limit defaults does not justify removing store checks. Sources: [core commit staging](../../packages/core/src/internal/virtualFileSystem.ts), [SQLite store](../../packages/persistence/src/SqliteLiveImageStore.ts), [R2 store](../../packages/persistence/src/R2LiveImageStore.ts).

## Stage two risks

The [issue comment](https://github.com/lloydrichards/effect-virtual-fs/issues/237#issuecomment-5904724598) proposes a required provider with memory and durable implementations, one `commit(candidate)`, required shutdown, and a shared internal test constructor. The shape matches the accepted commit-decorator design and removes the shared mutable `prepared` slot. Source: [persistent tree rebuild decision](../../.okf/decisions/core/persistent-tree-rebuild.md).

Folding prepare into commit must preserve the difference between a known staging failure and an uncertain storage outcome. Today encoding or size validation fails with `StorageRejected` while leaving the volume usable. Provider defects, interruption, and `unknown` disable it. A new provider interface must express definite preparation rejection without converting it into `OutcomeUnknown` or losing its cause. Source: [provider preparation and outcome classification](../../packages/core/src/internal/virtualFileSystem.ts).

Routing cleanup through commit changes durability behavior. Last-file release and removed-directory release currently have `applyDirect` paths that bypass storage. Cleanup must still release local handles when a store rejects or becomes uncertain, disable the volume when its durable state may disagree, and avoid retrying an uncertain commit. Scope finalizers cannot depend on ordinary admission permits. Sources: [file and directory cleanup](../../packages/core/src/internal/virtualFileSystem.ts), [durable lifecycle tests](../../packages/core/test/LiveVolume.test.ts).

A common memory and durable provider must also preserve interruption boundaries. Memory transitions currently run uninterruptibly once admitted, while durable transitions remain interruptible until commit begins. Removing the provider-undefined branch can silently change memory behavior. Treat that as a conscious design decision with regression coverage, or preserve the execution policy in the internal constructor. Source: [coordinated transition runner](../../packages/core/src/internal/virtualFileSystem.ts).

Recommended sequence is the limits fix first, followed by a separate provider refactor after cleanup and interruption decisions are settled. The first phase can land without changing `LiveImageStore` or `CommitOutcome`.
